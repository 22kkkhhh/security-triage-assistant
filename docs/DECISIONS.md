# 架构决策

## 安全事实与证据优先

- 决策：先记录可追溯事实、规则结果与证据，再由人工形成结论。
- 原因：技术异常本身不等于安全事件或数据泄露。
- 后果：产品输出使用“疑似”“建议核查”等措辞，不自动宣告入侵或违法。

## 人工最终决策

- 决策：HumanReview 是最终结论的唯一人工确认入口。
- 原因：安全与业务合理性需要人工判断。
- 后果：自动分析与调查进度均不得替代人工结论。

## UNKNOWN 与失败均 fail-closed

- 决策：缺失信息与运行时解析失败必须显式表达，不转换为空结果或正常状态。
- 原因：避免“未能判断”被误读为“没有问题”。
- 后果：UI 与报告流程必须区分成功、未知和不可用。

## 不作自动法律判断

- 决策：合规关联用于研判和核查辅助，不作违法、合规认证或法律意见结论。
- 原因：产品不是法律数据库或法律意见系统。
- 后果：Rule → Control → Clause 只提供可解释关联与核查依据。

## 不引入 RAG 或运行时 LLM Agent

- 决策：核心路径不依赖外部 AI API、RAG 或自主 Agent。
- 原因：保证范围、可解释性和最小化数据处理。
- 后果：规则可执行 SoT 保持在 TypeScript，知识包为受控数据。

## 报告合规引用必须冻结

- 决策：创建报告时固化 `complianceReferences`，后续保存与导出只消费该快照。
- 原因：知识包或运行时结果变化不能改写历史报告。
- 后果：报告保存必须保留已冻结引用，且采用 OCC 防止陈旧写入。

## 调查进度是投影

- 决策：InvestigationProgress 从服务端当前事实、清单和证据计算，不是最终案件状态。
- 原因：进度不能替代人工判断或案件状态机。
- 后果：服务端 DTO 是进度 SoT，客户端不得自行推导 OPEN/RESOLVED。

## Security Evidence 使用稳定身份与来源门控

- 决策：Security Evidence 身份为 `ruleId + actionId`，resolved 需要精确来源证明。
- 原因：展示标签可重复、顺序可变，业务上下文也不等同于安全验证证据。
- 后果：不得按 label 合并 checklist/evidence，也不得用 BusinessContext 自动完成安全验证。

## 已提供上下文不等于已收集证据

- 决策：Context supplied 与 Evidence collected 保持不同语义。
- 原因：字段存在并不证明核查已完成。
- 后果：进度、清单与报告必须分别展示缺失上下文和已收集证据。
